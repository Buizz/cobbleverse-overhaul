# 팀 프리뷰 및 전투 상태 승률 모델

> 상태: 설명 가능한 기준선 1차 구현
>
> 목표: 양쪽 팀 구성과 현재 전투 상태에서 최종 승리 확률을 추정하고, 그 확률을 높이는 행동을 선택한다.

- [x] 상대 행동 분포와 실제 1턴 상태를 포함한 기대 승률 `Q(s, a)` 계산
- [ ] `expert_winrate`의 후보 선택 기준을 완전한 기대 승률로 전환

현재 기준선 모델은 `heuristic-logistic-v3`다. 기존 상태 특징 점수를
로지스틱 함수에 통과시켜 확률 범위로 정규화하며, 아직 실제 승패 데이터로
보정된 통계 모델은 아니다. 따라서 현재 표시값은 AI 전환과 데이터 수집을 위한
일관된 기준선으로 사용하고, 실측 승률과 동일하다고 해석하지 않는다.

`v2`에서는 파티마다 에이스 후보 수가 다르다는 이유만으로 전원 생존 상태의
승률이 기울지 않도록 에이스 생존 수와 체력을 각 파티의 에이스 후보 수로
정규화한다. `fitWinProbabilityCalibration`은 전투 기록에서 보정 계수를
학습하지만, 단일 대진에서 얻은 계수는 기본 모델에 자동 적용하지 않는다.

`v3`에서는 현재 선발만 보지 않고 양쪽의 살아 있는 포켓몬을 모두 대조한다.
각 대면에서 예상 피해, 현재 HP, 우선도와 속도 순서를 계산한 뒤 다음 특징을
상태 가치에 추가한다.

- `matchupCoverage`: 각 상대 포켓몬을 상대로 가장 좋은 아군 대응 자원의 평균
- `safeKoCoverage`: 맞아 쓰러지기 전에 안전하게 KO할 수 있는 상대의 비율
- `benchReadiness`: 비활성 벤치의 HP, 상태 이상과 가장 좋은 대면의 종합 준비도
- `sweepPotential`: 한 포켓몬이 남은 상대 전체를 연속으로 돌파할 가능성

대면표는 `ThreatCounterMap`과 공유하고 같은 상태에서는 캐시한다. 실제 다음
상태를 만드는 2턴 탐색과 `expert_winrate`의 1턴 시뮬레이션은 이 특징을 각
탐색 노드에서 다시 계산한다. `expert_winrate`는 아군 상위 4개 후보와 상대
상위 2개 행동 분포를 조합한 최대 8개 전이를 평가한다. 명중·급소·피해 난수의
전체 확률 분포까지 펼치는 작업은 후속 개선으로 남아 있다.

## 1. 핵심 개념

기존의 기술별 고정 점수를 최종 판단 기준으로 사용하지 않는다. AI가 공통으로 비교할 값은 현재 상태의 승률 `V(s)`와 행동 이후 기대 승률 `Q(s, a)`다.

```text
V(s) = 현재 상태 s에서 최종적으로 승리할 확률

Q(s, a)
  = Σ 상대 행동 o의 확률
    × Σ 전투 결과 s'의 확률
    × V(s')

행동 가치 변화 = Q(s, a) - V(s)
```

일반 난이도에서는 공개 정보로 상대 행동 분포를 예측한다. 최고 치터 난이도에서는 이미 잠긴 상대 명령을 사용하되, 명중·급소·피해 난수와 이후 턴은 여전히 확률로 계산한다.

승률만 맹목적으로 최대화하지는 않는다. 불법 행동 제거, 에이스와 유일 카운터 보존, 전멸 위험 같은 전략 안전 제약을 먼저 적용한 뒤 남은 후보를 승률 변화로 비교한다.

## 2. 두 종류의 승률 평가기

### 2.1 `TeamPreviewValue`

전투 시작 전에 양쪽 멤버와 공개된 구성만 보고 초기 상성 승률을 추정한다. 다음 특징을 사용한다.

- 타입과 공격 범위, 상호 약점
- 예상 속도 구간과 선공기
- 판깔이·제거·회복 수단
- 물리·특수 막이와 돌파 수단
- 에이스 후보와 에이스를 막을 카운터
- 상태 이상, 날씨, 필드와 승리 조건의 시너지
- 공개되지 않은 기술·도구·특성에 대한 가설 분포

첫 출력 계약은 다음 형태를 목표로 한다.

```text
WinEstimate(
  probability,
  confidence,
  modelVersion,
  topFactors
)
```

`probability`는 승률, `confidence`는 현재 정보가 추정에 충분한 정도다. `topFactors`에는 “상대 물리 에이스를 막을 자원이 없음”처럼 사람이 검토할 수 있는 주요 근거를 남긴다.

### 2.2 `BattleStateValue`

전투가 시작된 뒤에는 `TeamPreviewValue`를 초기값으로 삼고 다음 실시간 상태를 반영해 `V(s)`를 갱신한다.

- 생존 멤버, 현재·최대 HP와 상태 이상
- 능력치 랭크, 사용 가능한 기술과 남은 PP
- 날씨, 필드, 설치물, 구속과 턴 제한 효과
- 남은 아이템·기믹·회복 등 소모성 자원
- 현재 대면 상성, 속도 관계와 교체 위험
- 양쪽 에이스와 카운터의 생존 가능성
- 선발과 벤치를 포함한 전원 대면 대응력과 안전한 KO 경로
- 전투 중 공개된 기술·특성·도구와 행동 이력

승리 또는 패배가 확정된 종단 상태는 각각 정확히 `1`과 `0`을 반환해야 한다.

## 3. 불완전 정보 처리

`expert` 이하 난이도는 플레이어가 볼 수 있는 정보만 사용한다. 미공개 기술·도구·특성은 확정값이 아니라 가능한 세트의 분포로 표현하고, 새로운 정보가 공개될 때 갱신한다.

- 모르는 정보를 가장 유리한 값으로 채우지 않는다.
- 가설이 넓을수록 `confidence`를 낮춘다.
- 상대 팀 전체가 공개되지 않는 규칙이라면 보이지 않는 멤버도 분포로 처리한다.
- 정보 정책을 위반한 특징이 모델 입력에 들어오면 해당 결정을 실패 처리하고 안전 AI로 전환한다.

이를 통해 높은 난이도와 치터 난이도의 차이가 단순 가중치가 아니라 **사용 가능한 정보의 차이**로 유지된다.

## 4. 행동 선택

한 턴의 기본 흐름은 다음과 같다.

1. 합법적인 기술·교체·아이템·기믹 후보를 생성한다.
2. 상대의 가능한 행동과 확률을 만든다.
3. 양쪽 행동 조합에 대해 명중, 급소, 피해 구간과 부가 효과를 시뮬레이션한다.
4. 각 다음 상태 `s'`의 `BattleStateValue`를 평가한다.
5. 확률을 합산해 각 후보의 `Q(s, a)`를 계산한다.
6. 전략 안전 제약을 통과한 후보 중 기대 승률이 높은 행동을 선택한다.
7. 거의 같은 후보에만 난이도별 제한 난수를 적용한다.

따라서 랭크업, 교체, 회복, 판깔이도 직접 피해가 없다는 이유로 낮게 평가되지 않는다. 최종 승률을 얼마나 바꾸는지가 공통 척도다.

## 5. 강화학습에 가까운 개선 순환

서버에서 플레이 중인 모델이 즉석으로 학습하게 하지는 않는다. 재현성, 악용 방지와 버전 관리를 위해 학습은 별도의 가상 대전 환경에서 오프라인으로 수행하고, Minecraft와 웹에는 검증된 추론 모델만 배포한다.

초기 개발 순서는 다음과 같다.

1. 설명 가능한 휴리스틱 `TeamPreviewValue`와 `BattleStateValue`를 기준선으로 만든다.
2. 기준 AI, 랜덤 AI, 기존 모델과 자기대전을 대량 실행한다.
3. 각 상태에 최종 승패와 남은 전투 결과를 연결해 학습 자료를 만든다.
4. 최종 승패를 더 잘 예측하도록 가치 모델을 학습한다.
5. 새 가치 모델로 행동 정책을 개선하고 다시 자기대전한다.
6. 규칙, 보정, 전략 장면과 성능 게이트를 통과한 모델만 승격한다.

이 구조는 강화학습의 `policy evaluation → policy improvement` 순환과 유사하다. 다만 첫 버전부터 거대한 종단간 모델을 사용하지 않고, 검증 가능한 전투 엔진과 작은 가치 모델을 결합한다.

## 6. 학습 및 평가 데이터

자기대전만 반복하면 서로의 약점을 공유하거나 한 가지 메타에 과적합할 수 있다. 학습·검증 조합에는 다음을 섞는다.

- 다양한 합법 팀과 역할 조합의 자기대전
- 랜덤, 최고 피해, 기존 점수제와 이전 모델
- 관장·리그·보스의 고정 팀
- 교체 반복, 랭크업 유도 등 악용을 노리는 적대적 스크립트
- 사용자 동의를 받아 익명화한 실제 전투 로그
- 유리·불리·비슷한 상성의 균형 잡힌 시작 상태

학습 세트와 승격용 고정 평가 세트는 분리한다. 고정 평가 팀을 학습에 다시 넣지 않는다.

## 7. 모델 배포 형식

첫 모델은 JVM과 JavaScript에서 동일하게 계산할 수 있는 로지스틱 회귀 또는 작은 다층 퍼셉트론을 우선 검토한다.

- 학습 도구는 Python 등을 사용할 수 있다.
- 특징 추출과 추론 계약은 Kotlin `commonMain`에 둔다.
- 가중치, 특징 스키마, 데이터 버전과 체크섬을 함께 버전 관리한다.
- JVM·JS의 동일 입력은 허용 오차 안에서 동일한 승률을 내야 한다.
- 모델을 읽지 못하거나 숫자가 비정상이면 설명 가능한 휴리스틱 모델로 전환한다.

복잡한 트리 모델이나 신경망은 작은 모델이 기준선을 넘지 못할 때만 도입한다.

## 8. 계산 실행 위치와 서버 부하

Minecraft 멀티플레이에서 전투의 최종 권위와 AI 행동 확정은 서버가 가진다. 그러나 탐색과 승률 추론을 Minecraft 서버의 메인 틱 스레드에서 직접 실행할 필요는 없다.

권장 실행 구조는 다음과 같다.

```text
Minecraft 메인 스레드
  → 불변 BattleObservation 생성
  → 서버 측 AI 작업 큐에 요청

AI Worker Pool
  → 후보 생성·결과 탐색·승률 추론
  → 행동 ID + 입력 해시 + 판단 근거 반환

Minecraft 메인 스레드
  → 전투가 아직 같은 상태인지 확인
  → 행동 합법성·정보 정책·제한 시간 검증
  → Cobblemon에 최종 명령 제출
```

### 8.1 배치 선택지

| 방식 | 권장 용도 | 장점 | 위험·제약 |
|------|-----------|------|-----------|
| 서버 메인 스레드 직접 계산 | 초기 단순 프로토타입 | 구현이 단순함 | 틱 정지와 동시 전투 부하 |
| 서버 프로세스 내부 Worker Pool | **기본 권장안** | 권위 유지, 직렬화 비용이 낮음 | 서버 CPU는 계속 사용 |
| 별도 신뢰 AI 서비스·프로세스 | 대형 서버의 확장안 | AI 부하와 장애를 게임 서버에서 격리 | 배포·통신·버전 관리 필요 |
| 플레이어 클라이언트 계산 | 싱글플레이·신뢰 환경·보조 표시 | 플레이어 장치 자원 활용 | 변조, 응답 거부, 정보 유출 |

### 8.2 클라이언트 위임의 제한

공개 멀티플레이에서 플레이어 클라이언트가 NPC의 최종 행동을 결정하게 하지는 않는다.

- 클라이언트가 응답을 변조해 고의로 약한 행동을 선택할 수 있다.
- 계산을 지연하거나 응답하지 않아 전투를 멈출 수 있다.
- 상대의 미공개 기술·도구·팀 구성이나 치터 난이도의 잠긴 명령을 보내면 정보가 유출된다.
- 모든 결과를 서버가 다시 계산해 검증하면 부하 절감 효과가 사라진다.
- 서로 다른 클라이언트 성능과 모드 상태 때문에 재현성이 깨질 수 있다.

클라이언트 계산을 허용할 수 있는 범위는 다음으로 제한한다.

- 싱글플레이 또는 운영자가 신뢰하는 폐쇄형 환경
- 브라우저 전투 실험실과 오프라인 자기대전
- 공개 정보만 사용하는 팀 프리뷰 승률·설명 UI
- 서버가 독립적으로 검증할 수 있는 후보 정렬 등의 보조 힌트

클라이언트 결과는 언제나 권고값이며, 서버가 입력 해시, 모델 버전, 정보 범위, 제한 시간과 행동 합법성을 검사한 뒤 채택한다. 미공개 정보와 잠긴 상대 명령은 클라이언트에 전송하지 않는다.

### 8.3 부하 제어

승률 모델 한 번의 추론보다 가능한 행동·상대 행동·난수 결과를 펼치는 탐색이 주된 비용이 될 가능성이 높다. 따라서 다음 장치를 함께 둔다.

- 전투별·난이도별 탐색 시간, 노드 수와 메모리 예산
- 동시 AI 작업 수와 플레이어별 요청 상한
- 동일 팀의 `TeamPreviewValue` 캐시
- 동일 상태·모델·정보 정책의 단기 결과 캐시
- 확정 KO, 강제 교체 등 단순 장면의 빠른 경로
- 부하가 높을 때 탐색 깊이와 결과 가지 수를 줄이는 단계적 축소
- 제한 시간 초과·워커 장애 시 결정론적 안전 AI 사용
- 큐 대기, 계산 시간, 취소, 시간 초과와 폴백 비율 계측

외부 AI 서비스는 확장 수단이지 필수 온라인 서비스가 아니다. 연결이 끊겨도 게임 서버가 로컬 안전 AI로 전투를 계속할 수 있어야 한다.

## 9. 난이도별 사용

| 난이도 | 승률 모델 사용 방식 |
|--------|---------------------|
| `novice` | 얕은 결과 예측, 낮은 정확도의 공개 정보와 의도적인 선택 오차 |
| `standard` | 팀 프리뷰와 1턴 기대 승률, 제한된 후보 |
| `expert` | 기존 휴리스틱 전문가. 기존 선택 동작과 회귀 테스트를 그대로 보존 |
| `expert_winrate` | 휴리스틱 후보 생성 후 상대 상위 행동과 실제 1턴을 시뮬레이션하고, 기대 승률이 2%p 이상 개선될 때만 선택 변경 |
| `cheater` | 잠긴 상대 행동을 알고 조건부 `Q(s, a)` 계산 |

난이도는 서로 다른 전투 규칙을 사용하지 않는다. 정보 범위, 탐색 예산, 모델 정밀도와 선택 정책만 다르게 한다.

## 10. 평가 지표

승률이 높게 보인다는 이유만으로 모델을 채택하지 않는다.

- **Brier score:** 예측 확률과 실제 승패의 제곱 오차
- **Log loss:** 과도하게 확신한 오답에 큰 페널티
- **ECE 및 신뢰도 도표:** 예측 70%인 상태가 실제로 약 70% 이기는지 확인
- 팀 상성·턴 구간·난이도별 보정 오차
- 행동 전후 평균 `Q(s, a) - V(s)`와 실제 승률 변화
- 기존 모델과의 쌍대 대전 승률 및 95% 신뢰 구간
- 학습 분포 밖 상태의 탐지율과 낮은 `confidence` 비율
- 동시 전투 수에 따른 큐 대기 시간, 추론 p95·p99와 시간 초과율
- 로컬 워커·외부 서비스·클라이언트 보조 경로별 결과 일치율

모델 승격은 전체 승률, 보정 정확도, 전략 장면, 규칙 적합성, JVM·JS 일치와 판단 시간 게이트를 모두 통과해야 한다.

## 11. 필수 테스트

- 승리·패배 종단 상태가 각각 `1`과 `0`인지 검증
- 양쪽 진영을 바꾸면 결과가 일관되게 반전되는지 검증
- 같은 모델·특징·시드에서 JVM과 JS 결과가 일치하는지 검증
- `cheater` 이외 프로필이 미공개 정보나 잠긴 명령을 사용하지 않는지 검증
- 공개 정보가 추가될 때 가설 분포와 신뢰도가 갱신되는지 검증
- 손상되거나 호환되지 않는 모델에서 안전 기준선으로 전환하는지 검증
- 에이스 보존, 유일 카운터, 랭크업 견제 장면에서 기대 승률이 합리적으로 변하는지 검증
- 오래 걸린 워커 결과가 이미 진행된 전투 상태에 적용되지 않는지 검증
- 클라이언트가 변조한 행동·입력 해시·모델 버전을 서버가 거부하는지 검증
- 워커 시간 초과와 외부 서비스 단절 시 안전 AI가 전투를 계속하는지 검증

## 12. 웹 실험실 표시

웹 버전은 최종 행동만 표시하지 않고 다음을 함께 보여준다.

- 팀 프리뷰 승률과 현재 전투 승률
- 후보 행동별 `Q(s, a)`와 현재 대비 변화량
- 승률에 영향을 준 주요 특징
- 턴별 승률 변화 그래프
- 모델·특징·전투 데이터 버전
- 여러 팀의 배치 대전 결과와 보정 보고서 내보내기

비교 실행:

```powershell
# 고정 대진
node scripts\compare-win-predictions.mjs 20260719 10 100 expert expert
node scripts\compare-win-predictions.mjs 20260719 10 100 expert_winrate expert_winrate

# 시드로 재현되는 무작위 6마리 엔트리 대진
node scripts\compare-win-predictions.mjs 20260730 10 100 expert expert --random-matchups --summary
node scripts\compare-win-predictions.mjs 20260730 10 100 expert_winrate expert_winrate --random-matchups --summary
```

2026-07-30 고정 10대진 기준으로 간이 델타 방식의 `expert_winrate`는 50%,
실제 1턴 상태를 사용하는 8전이 방식은 80%를 기록했다. 평균 엔진 시간은
약 204ms에서 약 542ms로 증가했다. 같은 평가에서 12전이는 77.5%/696ms,
6전이는 70%/396ms였으므로 현재 기본 예산은 8전이로 유지한다.

결과에는 학습 80%/홀드아웃 20%의 보정 Brier score, 정책이 실제로 변경한
행동, 휴리스틱 선택과 승률 최상 후보의 차이가 포함된다. 무작위 모드는 같은
시드에서 같은 엔트리 쌍을 선택하며, 자체 엔진이 지원하지 않는 특성을 가진
엔트리는 추첨 전에 제외한다. 메가폼처럼 실행 시점에만 드러나는 미지원 요소는
건너뛴 대진 수와 사유로 기록한다.

이는 AI의 강함뿐 아니라 잘못된 자신감과 특정 상성 편향을 찾는 디버깅 도구가 된다.

## 13. 완료 기준

- 양쪽 멤버만으로 초기 승률과 신뢰도를 계산할 수 있다.
- 전투 중 모든 주요 상태를 반영해 승률을 갱신할 수 있다.
- 기술·교체·아이템·기믹을 기대 승률이라는 같은 척도로 비교한다.
- 오프라인 자기대전으로 새 모델을 학습하고 이전 모델과 자동 비교할 수 있다.
- 승격된 모델이 Minecraft JVM과 웹 JavaScript에서 같은 계약으로 동작한다.
- 예측 승률의 보정 오차와 정보 정책 위반을 지속적으로 측정한다.
- Minecraft 메인 틱 스레드 밖에서 AI를 계산하고 시간 초과 시 안전하게 축소한다.
- 플레이어 클라이언트가 없어도 서버가 전투를 끝까지 진행할 수 있다.

## 14. 미결정 사항

- 첫 가치 모델을 로지스틱 회귀와 작은 다층 퍼셉트론 중 무엇으로 시작할 것인가?
- 팀 프리뷰에서 기술·특성·도구가 공개되는 범위는 전투 규칙별로 어떻게 다른가?
- 자기대전, 고정 팀, 이전 AI와 실제 로그의 학습 비율은 얼마인가?
- 한 턴 탐색에서 허용할 결과 가지 수와 시간 예산은 얼마인가?
- 모델 승격에 필요한 Brier score, ECE와 승률 개선 기준은 얼마인가?
- 사용자 전투 로그 수집을 기본 비활성으로 둘 것인가?
- 서버 내부 워커와 별도 AI 프로세스의 전환 기준은 동시 전투 몇 건인가?
- 공개 정보 기반 클라이언트 보조 계산을 실제 멀티플레이에 허용할 것인가?
