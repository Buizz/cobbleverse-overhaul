# 던전 입구 대기열·자동 매칭 시스템

> 관련 기능: F-05, F-07, F-09, F-15
>
> 관련 결정: 전역 파티나 사전 초대 없이, 던전 입장을 누른 플레이어를 입구 대기열에서 자동 매칭한다.
>
> 상위 설계: [데이터 기반 던전 생성 및 도전 시스템](DUNGEON_SYSTEM.md)
>
> 전투 설계: [특수 던전 2인 협동 멀티배틀](COOPERATIVE_DUNGEON_BATTLES.md)
>
> 설계 상태: 기준 계획 / 2인 자동 매칭 프로토타입 예정

## 1. 목적과 범위

던전 앞에서 입장을 선택한 플레이어가 별도 파티 생성·초대·파티장 지정 없이 같은 던전에 도전하려는 다른 플레이어와 자동으로 연결되게 한다.

- 전역 파티, 친구, 길드, 파티 채팅과 고정 그룹을 만들지 않는다.
- 입구 안내에서 `입장`을 누르는 행위 자체를 매칭 동의로 본다.
- 필요한 인원이 모이기 전에는 던전 슬롯이나 `DungeonRun`을 만들지 않는다.
- 매칭이 끝난 뒤에는 해당 실행 참가자만 `DungeonMatch`로 묶는다.
- 실행이 끝나면 매칭 관계도 종료한다.
- 협력형과 독립행동형은 같은 매칭 흐름을 사용하고 내부 이동·전투 규칙만 다르게 적용한다.

## 2. 사용자 흐름

```text
던전 입구 트리거
  → DungeonGuide 안내 화면
  → 플레이어가 입장 선택
  → 입장 조건 검사
  → DungeonEntryQueue 등록
  → "다른 도전자를 기다리는 중입니다" 표시
  → 다른 플레이어가 같은 입구에서 입장 선택
  → 서버가 대기 순서대로 자동 매칭
  → 두 참가자의 자격을 다시 검사하고 명단 잠금
  → 귀환점·DungeonPlan·슬롯 준비
  → 준비 완료 후 두 참가자를 함께 이동
  → 협력형 또는 독립행동형 던전 진행
  → 클리어·실패·포기 후 각자 귀환
  → DungeonMatch 종료
```

싱글 입장을 허용한 던전은 안내 화면에서 `혼자 입장`과 `2인 입장`을 구분할 수 있다. 정확히 2명이 필요한 던전은 `입장`을 누르면 바로 대기열로 들어간다.

## 3. 대기 화면

대기 중에는 다음과 같이 단순한 화면을 표시한다.

```text
다른 도전자를 기다리는 중입니다.

현재 인원 1 / 2
대기 시간 00:18

[대기 취소]
```

- 다른 대기자의 이름이나 포켓몬 파티는 표시하지 않는다.
- 화면을 닫거나 `대기 취소`를 누르면 대기열에서 빠진다.
- 입구 트리거 영역을 벗어나거나 다른 전투·이동을 시작해도 자동 취소한다.
- 매칭된 순간에는 취소 버튼을 잠그고 `던전을 준비하고 있습니다`로 바꾼다.
- 매칭 인원은 서버 상태를 실시간으로 반영하지만 실제 UUID 목록은 클라이언트가 결정하지 않는다.

입구 안내 화면에는 대기자가 있으면 `현재 1명이 기다리고 있습니다` 정도의 인원 정보만 보여 줄 수 있다. 대기자 신원은 노출하지 않는다.

## 4. 핵심 데이터 모델

```text
DungeonEntryRequest
  request_id
  player_uuid
  dungeon_id
  entrance_id
  match_pool_key
  dungeon_mode
  config_version
  state
  queued_at
  expires_at

DungeonMatch
  match_id
  dungeon_id
  entrance_id
  member_uuids
  dungeon_mode
  lifecycle_state
  created_at
  dungeon_run_id?
```

입장 요청 상태는 다음과 같다.

```text
WAITING
  → RESERVED
  → MATCHED
  → PREPARING
  → ACTIVE
  → CLOSED

WAITING → CANCELLED | EXPIRED
RESERVED | MATCHED | PREPARING → FAILED
```

- `WAITING`: 다른 참가자를 기다린다.
- `RESERVED`: 필요한 요청을 원자적으로 선점하고 중복 매칭을 막는다.
- `MATCHED`: 참가자 명단을 잠갔다.
- `PREPARING`: 귀환점, 계획과 슬롯을 준비한다.
- `ACTIVE`: `DungeonRun`에 참가자가 복사되어 실제 던전을 진행한다.
- `FAILED`: 준비 실패로 아무도 이동하지 않은 상태다.

활성 던전의 권위 상태는 `DungeonRun`이며, `DungeonMatch`는 어떤 입장 요청들이 같은 실행으로 묶였는지 기록한다.

## 5. 한눈에 보는 매칭 옵션

| 분류 | 옵션 키 | 가용 값 | 권고 기본값 |
|------|---------|---------|-------------|
| 입장 | `multiplayer.mode` | `solo`, `cooperative`, `independent` | 던전별 선택 |
| 인원 | `match.required_players` | 필요한 정확한 인원 | 초기 버전 2 |
| 범위 | `match.scope` | `same_entrance`, `same_dungeon` | `same_entrance` |
| 순서 | `match.order` | `fifo` | `fifo` |
| 대기 | `match.timeout_seconds` | 제한 없음 또는 최대 대기 시간 | 300초 |
| 시간 초과 | `match.on_timeout` | `cancel`, `keep_waiting`, `allow_solo` | `cancel` |
| 거리 | `match.stay_radius` | 대기 중 입구에서 벗어날 수 있는 거리 | 8블록 |
| 취소 | `match.cancel_on_ui_close` | 화면을 닫으면 대기 취소 | `true` |
| 취소 | `match.cancel_on_combat` | 다른 전투 시작 시 대기 취소 | `true` |
| 연결 종료 | `match.cancel_on_disconnect` | 대기 중 접속 종료 시 취소 | `true` |
| 준비 실패 | `match.on_prepare_failure` | `cancel`, `requeue_front` | `cancel` |
| 재매칭 | `match.requeue_cooldown_seconds` | 반복 취소 후 재등록 제한 | 기본 0초 |
| 협력 이동 | `multiplayer.tether` | 경고·최대 거리·복귀 정책 | 협력형 활성 |
| 협력 전투 | `multiplayer.battle_join` | `summon_all`, `require_nearby` | `summon_all` |
| 독립 보스 | `multiplayer.boss_join_policy` | `force_gather`, `ask_members`, `require_all_present`, `initiator_only` | `require_all_present` |
| 목표 | `multiplayer.progress_scope` | `shared`, `individual`, `mixed` | 협력형 `shared` |
| 전리품 | `loot.ownership` | `per_player`, `run_shared`, `first_claim` | `per_player` |

`same_entrance`는 실제로 같은 문 앞에서 입장한 플레이어끼리만 연결한다. 같은 던전에 여러 입구가 있어도 서로 섞이지 않으므로 귀환 위치와 입장 의도가 명확하다. 이후 대기 시간이 지나치게 길 때만 `same_dungeon` 확장을 검토한다.

## 6. 매칭 호환 조건

두 요청은 다음 값이 모두 호환될 때만 같은 실행으로 묶는다.

- 같은 `match_pool_key`
- 같은 던전 데이터·조각·전투 규칙 버전
- 같은 협력형 또는 독립행동형
- 같은 난이도·레벨 스케일링 선택
- 같은 반복 클리어·보상 자격 범주
- 플레이어가 다른 대기열, 던전, 전투나 이동 처리에 속하지 않음

권장 레벨은 기본적으로 안내값이므로 서로 비슷한 레벨끼리 억지로 분리하지 않는다. 던전이 실제 레벨 구간을 입장 조건으로 사용할 때만 같은 구간 요청끼리 매칭한다.

## 7. 대기열 등록과 취소

1. 플레이어가 안내 화면에서 `입장`을 누른다.
2. 서버가 입구, 진행 조건, 클리어 제한과 사용 가능한 포켓몬을 검사한다.
3. 플레이어가 다른 대기열이나 실행에 속하지 않았는지 확인한다.
4. `DungeonEntryRequest`를 만들어 해당 매칭 풀의 끝에 넣는다.
5. 대기 화면을 열고 서버가 입구 거리와 상태를 감시한다.

한 플레이어는 동시에 하나의 입장 요청만 가질 수 있다. 중복 클릭은 새 요청을 만들지 않고 기존 대기 화면을 다시 연다.

다음 상황에는 요청을 취소한다.

- 플레이어가 취소하거나 대기 화면을 닫음
- 허용 거리 밖으로 이동하거나 다른 차원·상위 공간으로 이동함
- 다른 전투, 거래, 컷신 또는 던전 입장 처리에 들어감
- 입장 필수 아이템·진행 조건을 잃음
- 접속 종료 또는 대기 시간 만료
- 입구나 던전 데이터 버전 변경

## 8. 원자적 자동 매칭

서버는 FIFO 순서로 필요한 수의 요청을 선택하고 한 번에 `RESERVED`로 바꾼다.

1. 가장 오래 기다린 호환 요청부터 선택한다.
2. 요청 잠금을 얻어 다른 매칭 작업이 가져가지 못하게 한다.
3. 모든 플레이어의 접속, 위치, 조건과 사용 가능한 포켓몬을 다시 검사한다.
4. 한 명이라도 실패하면 해당 요청을 취소하고 나머지는 원래 순서를 유지한다.
5. 모두 유효하면 `DungeonMatch`를 만들고 참가자 명단을 잠근다.
6. 이후에는 참가자 교체·추가·추방을 허용하지 않는다.

두 매칭 작업이 동시에 같은 플레이어를 가져가거나, 정원을 넘겨 매칭하는 일이 없어야 한다. 클라이언트가 보낸 상대 UUID나 순서를 신뢰하지 않는다.

## 9. 던전 준비 트랜잭션

매칭 이후 실제 입장도 전원 성공 또는 전원 취소로 처리한다.

1. 참가자별 현재 위치와 상위 공간을 `ReturnFrame`으로 저장한다.
2. 레벨 스케일링용 각 참가자의 포켓몬 파티 스냅샷을 기록한다.
3. `DungeonPlan`을 선택·생성하고 검증한다.
4. 슬롯, 내부 시작점과 참가자 안전 마커를 준비한다.
5. `DungeonRun`을 만들고 `match_id`와 참가자 UUID를 기록한다.
6. 모든 준비가 성공한 뒤에만 두 참가자를 이동한다.

준비에 실패하면 어느 참가자도 이동시키지 않는다. 기본적으로 매칭을 종료하고 오류를 안내한다. 일시적 서버 부하로 재대기가 더 나은 경우에만 `requeue_front`를 사용하며, 무한 생성 실패 반복을 막아야 한다.

## 10. 던전 내부 관계

매칭은 함께 입장할 사람만 정한다. 던전 내부 행동은 `multiplayer.mode`가 결정한다.

| 항목 | `cooperative` | `independent` |
|------|---------------|---------------|
| 이동 | 거리 제한을 두고 함께 진행 | 같은 슬롯에서 따로 탐색 |
| 일반 적 | 플레이어 2명 대 NPC 2명 `GEN_9_MULTI` | 각 플레이어가 NPC와 별도 더블배틀 |
| 전투 집결 | 안전 마커로 동료를 이동 | 일반 조우에는 집결하지 않음 |
| 목표 | 기본 공유 | 개인·공유·혼합 선택 |
| 보스 | 전원 참여가 기본 | 보스 합류 정책 선택 |
| 이탈 | 기본적으로 실행 실패 | 조건을 만족하면 남은 플레이어 계속 가능 |

파티장이나 추방 권한은 존재하지 않는다. 실행 중 한 사람이 나가더라도 다른 플레이어가 그 사람을 제거한 것이 아니라 던전의 이탈 정책이 적용된다.

## 11. 이탈·재접속·악용 방지

- 대기 중 접속 종료는 즉시 요청 취소로 처리한다.
- 매칭 후 준비 중 연결이 끊기면 입장을 취소하고 아무도 이동시키지 않는다.
- 활성 실행의 접속 종료에는 던전의 재접속 유예 시간을 적용한다.
- 협력형은 유예 중 필수 전투와 전원 퍼즐을 막고, 만료 시 기본적으로 실행을 실패시킨다.
- 독립행동형은 남은 플레이어가 목표·인원 조건을 만족하면 계속할 수 있다.
- 반복적으로 매칭 직후 이탈하는 플레이어에게는 운영 데이터 확인 후 짧은 재등록 제한을 적용할 수 있다.
- 보상과 진행은 `run_id + player_uuid`를 기준으로 처리하고 상대방의 이탈 여부만으로 중복 지급하지 않는다.

초기 버전은 평판, 신고, 탈주 점수와 강한 제재 시스템을 만들지 않는다. 실제 악용이 확인되면 가벼운 재대기 시간부터 추가한다.

## 13. 구현 순서

### 1단계: 안내 화면과 싱글 입장

- `DungeonGuide`의 입장·취소와 트리거 재발동 방지를 구현한다.
- 입장을 누른 뒤에만 계획과 슬롯을 준비한다.

### 2단계: 2인 입구 대기열

- `DungeonEntryRequest`, 대기 화면, 취소와 거리 감시를 구현한다.
- 같은 입구의 FIFO 요청 두 개를 원자적으로 매칭한다.

### 3단계: 준비와 귀환

- 전원 재검증, 명단 잠금, 계획·슬롯 준비와 동시 이동을 연결한다.
- 준비 실패 시 아무도 이동하지 않는지 검증한다.

### 4단계: 협력형·독립행동형

- 협력형 집결과 `GEN_9_MULTI`를 구현한다.
- 독립행동형 개인 조우·상자·목표 잠금과 보스 합류 정책을 구현한다.

### 5단계: 운영 보강

- 대기 시간, 취소율, 준비 실패율과 실행 이탈률을 기록한다.
- 측정 결과에 따라 시간 초과, 재대기와 가벼운 취소 제한을 조정한다.

## 14. 합격 기준

1. 안내 화면만 열거나 취소한 플레이어는 대기열에 들어가지 않는다.
2. 입장을 누른 첫 플레이어에게 다른 도전자를 기다린다는 화면이 표시된다.
3. 두 번째 호환 플레이어가 입장하면 두 요청이 정확히 한 번 매칭된다.
4. 다른 입구, 다른 규칙 버전과 다른 던전 요청이 잘못 섞이지 않는다.
5. 같은 플레이어가 여러 대기열이나 매칭에 동시에 포함되지 않는다.
6. 대기자가 입구를 떠나거나 접속 종료하면 요청이 제거된다.
7. 매칭 후 한 명의 자격이 사라지면 어느 누구도 던전으로 이동하지 않는다.
8. 준비 성공 시 두 참가자가 같은 `DungeonRun`으로 이동한다.
9. 협력형과 독립행동형이 각자 설정된 이동·전투 규칙을 따른다.
10. 클리어·실패·재접속 후 각 참가자가 자신의 입구 귀환점으로 돌아간다.
11. 보상과 진행이 참가자별로 정확히 한 번 기록된다.

## 15. 초기 확정안

- 전역 파티와 사전 초대는 구현하지 않는다.
- 입장 버튼을 누르면 같은 입구의 FIFO 대기열에 등록한다.
- 첫 구현은 정확히 2명을 요구하고 같은 입구 요청끼리만 매칭한다.
- 첫 플레이어에게 `다른 도전자를 기다리는 중입니다`와 취소 버튼을 표시한다.
- 두 번째 플레이어가 입장하면 별도의 파티장·준비 투표 없이 서버가 자격을 다시 검사하고 준비를 시작한다.
- 매칭 후에는 참가자 추가·교체·추방을 허용하지 않는다.
- 협력형은 두 플레이어 대 NPC 두 명, 독립행동형은 각자 일반 조우를 진행한다.
- 실행 종료와 함께 `DungeonMatch`도 종료한다.
