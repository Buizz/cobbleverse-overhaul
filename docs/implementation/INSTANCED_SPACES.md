# 공용 인스턴스 차원과 상태 변화 건물

> 관련 기능: F-15 공용 인스턴스 공간
>
> 관련 결정: D-21 레이드 덴식 인스턴스 패턴의 적용 범위
>
> 설계 상태: 기술 참고안 / 프로토타입 후 적용 범위 확정

## 1 목적

Cobblemon Raid Dens처럼 고정된 공용 공허 차원 하나에 서로 멀리 떨어진 슬롯을 할당하고, 필요한 구조물 템플릿을 배치해 전투장·건물 내부·연출 공간으로 사용한다. 레이드마다 동적 차원을 새로 만들지 않으므로 차원 등록과 백업 대상을 제한하면서 동시에 여러 인스턴스를 격리할 수 있다.

이 패턴은 다음 두 용도로 검토한다.

1. 종료 후 제거되는 관장전·레이드·리그전·컷신 공간
2. 스토리 진행도에 따라 내부 구조와 NPC가 달라지는 집·상점·연구소 등의 상태 변화 공간

특수 던전의 2인 협동 입장, 던전 세션과 EasyNPC 보스 멀티배틀은 [특수 던전 2인 협동 멀티배틀](COOPERATIVE_DUNGEON_BATTLES.md)을 따른다.

## 2 참고 구현: Cobblemon Raid Dens

조사 기준은 Minecraft 1.21.1, Cobblemon 1.7.3용 Cobblemon Raid Dens `0.11.4` 공개 소스다.

Raid Dens는 레이드마다 차원을 생성하지 않는다. `cobblemonraiddens:raid_dimension`이라는 고정 공허 차원 하나를 등록하고, 동시 레이드를 약 2,000블록 간격의 좌표 슬롯에 배치한다.

```text
오버월드 레이드 크리스탈 사용
  → 비어 있는 레이드 슬롯 할당
  → 공용 레이드 차원에 NBT 전투장 배치
  → 보스 생성·청크 로드 티켓 추가
  → 플레이어의 출발 차원·좌표 저장
  → 전투장 좌표로 이동
  → 종료 시 원위치 복귀
  → 엔티티·블록 엔티티·구조물 제거
  → 청크 로드 티켓과 슬롯 반환
```

이 방식에서 참고할 핵심은 다음과 같다.

- 차원은 서버 시작 시 고정 등록하고 인스턴스만 런타임에 할당한다.
- 슬롯은 서로 충분히 멀리 두고 각 슬롯의 보호 경계를 명시한다.
- 구조물 NBT에 플레이어 시작점, 보스 위치와 귀환 블록 위치를 정의한다.
- 입장 전에 원래 차원과 좌표를 저장한다.
- 서버 재시작·재접속 시 인스턴스에 갇히지 않도록 안전 귀환 데이터를 저장한다.
- 활성 슬롯에만 청크 로드 티켓을 부여하고 종료 시 제거한다.
- 정리 순서는 플레이어 귀환, 엔티티 제거, 블록 초기화, 슬롯 반환으로 고정한다.

## 3 Cobbleventure 적용 구조

초기안은 역할별 공용 차원을 하나씩 두는 방식이다.

```text
cobbleventure:instances
  ├─ 슬롯 0: 임시 관장전 경기장
  ├─ 슬롯 1: 레이드 또는 보스전
  ├─ 슬롯 2: 스토리 컷신 공간
  └─ 슬롯 N: 상태 변화 건물 내부

cobbleventure:farm_plots
  └─ 플레이어별 영구 1청크 농장
```

개인 농장은 장기 보존과 상시 로드 정책이 다르므로 일반 인스턴스 차원과 분리한다. 반대로 짧은 전투장과 컷신 방은 같은 `instances` 차원에서 슬롯만 달리해도 된다.

| 공간 유형 | 수명 | 종료 시 처리 | 저장 대상 |
|-----------|------|--------------|-----------|
| 관장전·레이드 | 수분~수십 분 | 구조물 전체 초기화 | 참가자, 전투 결과, 귀환점 |
| 리그 도전 방 | 도전 세션 | 도전 종료 후 초기화 또는 짧게 캐시 | 사천왕 순서, 승패, 귀환점 |
| 컷신·이벤트 방 | 연출 세션 | 즉시 초기화 | 시청 여부, 선택 결과 |
| 개인 스토리 건물 | 플레이어 진행 기간 | 슬롯 재사용 가능, 논리 상태는 보존 | 스토리 단계, NPC, 컨테이너 정책 |
| 서버 공용 건물 | 장기 | 자동 삭제하지 않음 | 서버 공용 스토리 단계와 구조물 버전 |

## 4 슬롯 할당

각 슬롯은 인덱스에서 결정되는 중심 좌표와 보호 경계를 가진다.

```text
InstanceSlot
  slot_index
  centre
  bounds
  instance_type
  owner_scope
  template_id
  template_version
  lifecycle_state
  return_anchors
  active_players
```

- 슬롯 간 거리는 최대 구조물 크기, 렌더 거리, 소리·파티클과 엔티티 탐색 범위를 고려해 정한다.
- 임시 슬롯은 빈 공간을 재사용하고 영구 슬롯은 안정된 소유 ID에 매핑한다.
- `player UUID + building ID`처럼 재현 가능한 키를 사용하면 서버 재시작 후 같은 논리 공간을 복구하기 쉽다.
- 슬롯의 실제 좌표를 진행 데이터로 사용하지 않고 별도 인덱스에 저장한다.
- 슬롯 할당 상한과 대기·거부 정책을 설정해 무한한 동시 생성을 막는다.

## 5 스토리 진행에 따른 집·건물 변화

### 5.1 외관과 내부 분리

세대 월드의 건물 외관은 모든 플레이어에게 공유하고, 문이나 입구를 사용하면 공용 인스턴스 차원의 내부로 이동시키는 방식을 우선 검토한다.

```text
세대 월드의 시작 집 외관
  → 문 사용
  → 플레이어의 story_stage 조회
  → home/interior_stage_2.nbt 선택
  → 해당 플레이어의 내부 슬롯 준비
  → 내부로 이동
```

이 구조를 사용하면 같은 건물 입구를 사용해도 플레이어별 진행도에 따라 다음처럼 다른 내부를 보여줄 수 있다.

- 초반: 이사 상자와 비어 있는 방
- 첫 배지 이후: PC, 지도와 농장 접속 장치 활성화
- 중반: 트로피, 사진, NPC 대사와 장식 추가
- 리그 완료: 전당 기록, 챔피언 트로피와 후속 퀘스트 오브젝트 추가
- 사건 진행: 파손·점거·복구된 연구소 또는 상점 내부

### 5.2 상태 범위

| 범위 | 예시 | 구현 방식 |
|------|------|-----------|
| 플레이어 개인 | 자기 집, 개인 퀘스트 방, 개인 라이벌 이벤트 | 플레이어별 스토리 플래그와 내부 슬롯 |
| 파티 공유 | 협동 퍼즐방, 팀 기지 이벤트 | 파티 ID별 상태와 슬롯 |
| 서버 공용 | 마을 복구, 리그 개장, 공용 연구소 변화 | 서버 공용 플래그와 영구 구조물 버전 |

서버 공용 외관이 바뀌는 사건을 플레이어별 인스턴스로만 표현하면 밖에서 본 모습과 내부가 어긋날 수 있다. 모든 플레이어가 봐야 하는 도시 외관 변화는 실제 세대 월드 구조물, 블록 디스플레이 또는 단계별 장식 레이어로 처리하고, 개인별 차이는 내부·NPC·상호작용에 한정한다.

### 5.3 템플릿 전환

스토리 단계가 바뀌었다고 플레이어가 들어 있는 건물 구조물을 즉시 덮어쓰지 않는다.

```text
story_stage 변경
  → 다음 입장에 사용할 template_version 갱신
  → 현재 이용자가 없을 때 슬롯 잠금
  → 보존 대상 데이터 추출
  → 기존 임시 구조물 정리
  → 새 NBT 템플릿 배치
  → NPC·상호작용·장식 상태 복원
  → 검증 후 슬롯 개방
```

- 이용자가 있으면 퇴장 후 전환하거나 안전 대기실로 이동시킨다.
- 상자 안 아이템처럼 플레이어가 바꿀 수 있는 데이터는 구조물 NBT와 분리한다.
- 템플릿 전환 실패 시 직전 버전으로 되돌릴 수 있어야 한다.
- `template_id`, `template_version`, `story_stage`를 함께 저장한다.
- 단계가 내려가거나 퀘스트를 초기화할 때의 역방향 전환 정책도 정의한다.

## 6 입장·귀환 안전장치

- 입장 전에 출발 차원, 정확한 좌표, 회전, 게임 모드와 탑승 상태를 서버에 저장한다.
- 목적지 구조물과 필수 블록이 준비되기 전에는 플레이어를 이동시키지 않는다.
- 로그아웃 저장 시 인스턴스가 유효하지 않으면 안전 귀환점에서 재접속시킨다.
- 사망, 서버 재시작, 관리자 이동과 다른 모드의 텔레포트도 세션 종료로 처리할지 정의한다.
- 활성 포켓몬은 이동 전에 회수하고 입장 후 허용된 경우 다시 소환한다.
- 슬롯 정리 전 경계 안의 모든 플레이어를 먼저 귀환시킨다.
- 귀환 차원이나 좌표가 사라졌다면 시작 마을 PC 앞 같은 다단계 대체 앵커를 사용한다.

## 7 보호와 게임 규칙

- 인스턴스 차원도 서바이벌 모드를 유지하고 템플릿별 서버 보호 프로필을 적용한다.
- 구조물 파괴·설치·임의 컨테이너 사용은 태그로 허용된 블록만 가능하게 한다.
- 슬롯 경계를 벗어나면 입장점으로 되돌린다.
- 엔더 진주, 비인가 비행, 포탈과 다른 모드 워프를 차단한다.
- 다른 슬롯의 엔티티·소리·보스바·전투 상태가 보이지 않도록 영역 필터를 적용한다.
- 임시 전투장의 드롭 아이템과 엔티티는 종료 시 명시적으로 정리한다.

## 8 Raid Dens를 사용하는 방법과 자체 구현의 경계

기존 Cobblemon Raid Dens는 레이드 보스와 전투장 구조물을 데이터팩으로 확장할 수 있으므로 일반 레이드는 해당 확장 기능을 우선 사용한다. 프로젝트가 직접 구현할 대상은 다음과 같다.

- 관장전·리그·컷신처럼 Raid Dens 전투 규칙과 다른 인스턴스
- 플레이어별 스토리 건물 내부
- 템플릿 버전 전환과 상태 보존
- 본가식 가방, 진행 플래그와 PC 개인 농장 연동

Raid Dens 코드를 그대로 복사하기보다 슬롯 할당, 귀환 저장, 청크 티켓과 정리 순서라는 설계 패턴을 참고한다. 소스 재사용이 필요하면 MIT 라이선스 고지와 변경 내역을 보존한다.

## 9 프로토타입

첫 프로토타입은 같은 공용 공허 차원에 두 종류의 슬롯을 만든다.

1. 종료 시 완전히 초기화되는 작은 관장전 방
2. `story_stage` 0·1·2에 따라 템플릿이 바뀌는 플레이어 집 내부

### 합격 기준

- 두 명이 동시에 서로 다른 슬롯을 사용해도 구조물·NPC·보스바가 섞이지 않는다.
- 플레이어의 출발 위치가 각각 저장되고 정상·사망·재접속·서버 재시작 후 안전하게 복귀한다.
- 빈 슬롯이 재사용되고 활성 슬롯은 잘못 초기화되지 않는다.
- 집 내부가 스토리 단계에 맞는 템플릿으로 바뀐다.
- 템플릿 교체 중 컨테이너 아이템과 진행 상태가 유실·복제되지 않는다.
- 구조물 배치 실패 시 플레이어를 이동시키지 않고 직전 상태로 복구한다.
- 비활성 슬롯의 청크 로드 티켓이 제거된다.

## 10 미결정 사항

- 전투·컷신·건물 내부를 한 차원에 둘 것인가, 역할별로 분리할 것인가?
- 슬롯 간격과 슬롯당 최대 경계는 얼마인가?
- 동시에 유지할 임시 인스턴스 상한은 몇 개인가?
- 집 내부 슬롯은 입장할 때마다 재구성할 것인가, 일정 시간 캐시할 것인가?
- 건물 내부의 컨테이너와 NPC 상태를 어디까지 영구 저장할 것인가?
- 서버 공용 마을 외관 변화를 구조물 교체와 장식 레이어 중 무엇으로 구현할 것인가?
- Raid Dens를 필수 의존성으로 둘 것인가, 설계 패턴만 참고할 것인가?
