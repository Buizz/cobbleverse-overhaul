# 월드 생성 및 체육관 도시 배치

> 관련 요구사항: F-01, 프로젝트 기획서 4.1·6.2·7장
>
> 관련 결정: D-04 도시 배치 방식, D-05 기존 월드 지원 범위
>
> 설계 상태: 기술 조사 진행 / 구현 버전과 API 미확정

## 1 목적

체육관, 마을 건물, 상점과 영구 NPC 기준점을 하나의 `체육관 도시`로 생성한다. 같은 월드 시드와 설정에서는 같은 결과를 재현하고, 필수 도시의 누락·중복과 플레이어 건축물 훼손을 방지해야 한다.

## 2 마인크래프트 구조물 구성

마인크래프트의 마을은 완성된 마을 하나를 복사하는 방식이 아니라 여러 계층을 조합해 생성한다.

| 구성 요소 | 역할 |
|-----------|------|
| 구조물 템플릿 | 건물이나 도로 한 조각을 저장한 `.nbt` 파일 |
| 직소 블록 | 다음 구조물 조각이 연결될 위치와 방향을 표시 |
| 템플릿 풀 | 후보 조각과 선택 가중치를 정의 |
| 구조물 정의 | 시작 풀, 조립 깊이, 높이, 허용 바이옴과 지형 적응을 정의 |
| 구조물 세트 | 구조물 간격과 분포 알고리즘을 정의 |
| 프로세서 목록 | 배치 중 블록 교체, 노후화와 지형 적응을 수행 |

큰 도시는 체육관, 센터, 상점, 주택, 도로와 장식 조각으로 나눈다. 필수 건물은 항상 이어지는 전용 풀에 넣고, 주택과 장식만 가중치 기반으로 선택한다.

## 3 구조물 제작과 반입 절차

1. 실제 배포 환경과 같은 버전의 별도 건축용 인스턴스를 만든다.
2. WorldEdit 또는 Axiom으로 테스트 월드에서 구조물을 제작한다.
3. 외부 `.schem`, `.litematic` 또는 월드 파일은 테스트 월드에 반입해 수정한다.
4. 각 조각에 직소 블록과 구조물 원점을 배치한다.
5. 구조물 블록으로 프로젝트 네임스페이스의 `.nbt` 파일을 저장한다.
6. 데이터팩의 템플릿 풀, 구조물과 구조물 세트 JSON을 작성한다.
7. `/place template`, `/place jigsaw`, `/place structure`로 개별 조각부터 전체 도시까지 검증한다.
8. 여러 시드와 바이옴에서 자연 배치, 충돌과 재현성을 검증한다.

Minecraft 1.21 이상에서는 구조물 블록의 출력 폴더와 데이터팩의 입력 폴더 이름이 다르다.

```text
# 구조물 블록 출력
saves/<world>/generated/cobbleverse_overhaul/structures/<name>.nbt

# 데이터팩 입력
data/cobbleverse_overhaul/structure/<name>.nbt
```

프로젝트의 실제 대상 버전을 고정한 뒤 폴더명과 데이터팩 포맷을 다시 확인한다.

## 4 고정 좌표 배치 선택지

### 4.1 명령 기반 일회성 배치

초기 프로토타입은 지정 좌표에서 지표면 높이를 계산한 뒤 `/place structure`를 실행하는 방식이 가장 단순하다.

```mcfunction
forceload add 1000 1000
execute positioned 1000 0 1000 positioned over motion_blocking_no_leaves run place structure cobbleverse_overhaul:gym_town ~ ~ ~
data modify storage cobbleverse_overhaul:world gym_town_01 set value 1b
forceload remove 1000 1000
```

다시 실행해 도시를 겹쳐 놓지 않도록 저장 상태를 먼저 검사한다.

```mcfunction
execute unless data storage cobbleverse_overhaul:world {gym_town_01:1b} run function cobbleverse_overhaul:setup/place_gym_town_01
```

이 방식은 실험과 관리자 수동 배치에는 적합하지만, 지형 적합성 검사와 부분 실패 복구가 제한적이다.

### 4.2 코어 모드 기반 결정론적 배치

정식 구현은 코어 모드가 다음 순서로 도시 위치를 결정하고 월드 저장 데이터에 기록하는 방식을 권고한다.

1. 월드 시드, 설정과 도시 ID로 기준 좌표를 계산한다.
2. 기준점 주변 후보를 항상 같은 순서로 탐색한다.
3. 바이옴, 경사, 수면, 구조물 충돌과 월드 경계를 검사한다.
4. 가장 먼저 통과한 후보를 실제 좌표로 확정한다.
5. 도시 구조물과 NPC 마커를 생성한다.
6. 도시 ID, 기준 좌표, 실제 좌표와 구조물 버전을 저장한다.

기준 좌표를 그대로 사용할 수 없는 경우에도 후보 탐색 순서가 같으면 같은 시드에서 같은 실제 위치를 얻을 수 있다.

## 5 황혼의 숲 사례 조사

### 5.1 조사 기준

- 대상: Twilight Forest Minecraft 1.21.1 브랜치
- 확인 커밋: `67117c1ed7552febb4cbd67980895f3307385711`
- 확인 항목: 랜드마크 격자, 핵심 바이옴 레이어, 구조물 세트와 바이옴 태그

### 5.2 생성 원리

황혼의 숲은 대략 `16×16청크`, 즉 `256×256블록` 영역마다 랜드마크 후보 슬롯을 둔다. 슬롯 중심은 영역 중앙에서 최대 약 3청크 범위로 이동하지만, 같은 영역에는 항상 같은 계산식을 적용한다.

바이옴 생성기는 다음 네 핵심 바이옴을 격자와 정렬된 위치에 배치한다.

```text
glacier
fire_swamp
dark_forest_center
final_plateau
```

각 핵심 바이옴 주변에는 진행 단계에 맞는 동반 바이옴을 배치한다.

| 핵심 바이옴 | 동반 바이옴 | 주요 구조물 |
|-------------|-------------|-------------|
| `glacier` | `snowy_forest` | 오로라 궁전, 예티 동굴 |
| `fire_swamp` | `swamp` | 히드라 소굴, 미궁 |
| `dark_forest_center` | `dark_forest` | 다크 타워, 기사 요새 |
| `final_plateau` | `highlands` | 최종 성, 트롤 동굴 |

구조물 세트는 커스텀 `landmark_grid` 배치를 사용해 격자 중심만 후보로 허용한다. 각 보스 구조물은 별도의 바이옴 태그를 가지므로 후보 중심의 바이옴과 일치하는 구조물만 실제로 생성된다.

```text
월드 시드
  → 랜드마크 격자와 후보 중심
  → 격자에 맞춘 핵심·동반 바이옴
  → 구조물별 바이옴 필터
  → 해당 슬롯의 보스 구역 생성
```

일반 숲에서 생성되는 나가 정원, 리치 타워와 언덕 구조물은 격자 슬롯을 시드 기반으로 나눠 사용하며, 보스 진행 바이옴 구조물과 다른 선택 규칙을 사용한다.

### 5.3 프로젝트에 적용할 결론

황혼의 숲은 전용 차원의 바이옴 생성기까지 통제하기 때문에 격자와 보스 바이옴을 강하게 결합할 수 있다. Cobbleverse 오버월드에서 같은 방식을 그대로 사용하면 다른 바이옴·월드 생성 모드와 충돌할 가능성이 높다.

체육관 도시는 다음처럼 진행 기능과 외형을 분리한다.

- 도시 ID와 진행 순서는 고정 좌표 목록 또는 결정론적 격자로 결정한다.
- 바이옴은 사막형, 설원형, 평원형 같은 도시 외형을 선택한다.
- 필수 체육관과 진행 거점은 부적합한 바이옴 때문에 누락되지 않아야 한다.
- 바다, 급경사와 다른 대형 구조물은 후보에서 제외하고 인근 적합지를 찾는다.
- 최종 좌표를 월드 데이터에 저장해 업데이트 후에도 움직이지 않게 한다.

## 6 권고 도시 배치 규칙

첫 수직 구간은 다음 기본안을 검증한다.

```text
고정된 도시 ID와 기준 좌표
  → 반경 내 후보 좌표 생성
  → 바이옴·경사·수면·충돌 검사
  → 바이옴별 외형 선택
  → 필수 건물과 선택 건물 조립
  → 도시 상태 저장
```

도시 위치 계산과 외형 선택을 분리하면 콘텐츠 순서를 유지하면서도 주변 환경에 자연스럽게 맞출 수 있다.

## 7 본가식 필드, 대륙과 서식지 구역

### 7.1 지형과 서식지를 분리한다

하나의 마인크래프트 바이옴을 하나의 포켓몬 서식지로 간주하지 않는다. 월드의 물리적 지형 위에 별도의 `지역(region)`과 `서식지(habitat)` 계층을 겹치는 방식을 권고한다.

```text
물리 지형: 평원, 숲, 산, 바다, 동굴
  + 지역: 서부 대륙, 동부 대륙, 1번 도로, 화산권
  + 미세 서식지: 지상, 지하, 수중, 폐광, 마을 주변
  + 상태: 시간, 날씨, 진행도, 이벤트
  = 실제 포켓몬 스폰 풀
```

이렇게 하면 겉보기에는 같은 평원이어도 `region_id`나 좌표 범위에 따라 서로 다른 포켓몬을 배치할 수 있다. Cobblemon 기본 스폰 조건은 바이옴 외에도 좌표 범위, 차원, 구조물, 높이, 광량, 하늘 노출, 주변·바닥 블록, 시간과 날씨를 지원한다.

초기 데이터팩에서는 `minX/maxX/minZ/maxZ`로 직사각형 지역을 나누고, 동굴은 `canSeeSky: false`, 높이와 주변 블록 조건으로 구분한다. 복잡한 경계나 플레이 진행 플래그까지 스폰 조건에 넣으려면 코어 모드에 커스텀 지역 판정과 Cobblemon 스폰 연동을 구현한다.

### 7.2 본가식 필드 구성

본가식 도로와 필드는 완전 무작위 생성보다 다음 요소를 결정론적으로 배치하는 편이 적합하다.

- 도시, 체육관, 동굴 입구와 스토리 거점은 고정 앵커 또는 결정론적 격자로 배치한다.
- 거점 사이의 이동 회랑을 `route_id`로 정의한다.
- 회랑 내부의 지형과 장식은 자동 생성하되 필수 이동 경로와 이벤트 위치는 보장한다.
- 지름길, 비밀 지역과 수집 요소는 구조물 조각으로 변주한다.

자동 지형 위에 본가식 진행 동선을 얹는 혼합 방식이며, 완전 수작업 맵보다 시드 다양성과 모드 호환성을 유지하기 쉽다.

### 7.3 펠월드식 대륙

대륙의 해안선, 산맥과 지역 순서를 모두 의도대로 만들려면 일반 바이옴 데이터팩만으로는 부족하다. 선택지는 다음과 같다.

| 방식 | 장점 | 단점 | 권고 용도 |
|------|------|------|-----------|
| 기존 자동 지형 + 지역 오버레이 | 호환성과 개발 속도가 좋음 | 대륙 형태를 강제할 수 없음 | 1차 구현 |
| 저주파 노이즈·보로노이 기반 커스텀 생성기 | 큰 대륙과 지역을 재현 가능 | 월드 생성 코드와 호환성 비용이 큼 | 장기 확장 |
| WorldPainter 등으로 제작한 고정 월드 | 원하는 해안선과 동선을 정확히 제작 | 무한 랜덤 월드가 아니며 업데이트가 어려움 | 스토리 중심 서버/맵 |
| 전용 차원 | 오버월드와 충돌 없이 완전 통제 | 차원 이동 UX와 별도 호환성 설계 필요 | 강한 본가식 구성 |

첫 버전에서는 대륙 생성기를 새로 만들지 않고 좌표 기반 대지역과 고정 거점을 기존 자동 지형에 얹는다. 게임성이 검증된 뒤 전용 차원 또는 커스텀 생성기로 확장한다.

### 7.4 동굴 구현

동굴 자체는 구현 가능하지만 목표에 따라 난도가 크게 다르다.

- **자연 동굴 서식지:** 바닐라 자동 동굴을 그대로 사용하고 하늘 노출, Y좌표, 광량, 주변 광물과 블록으로 스폰 풀을 나눈다.
- **이름 있는 탐험 동굴:** 고정 입구와 지하 직소 구조물 조각을 연결한다. 방, 통로, 보스방과 출구를 보장하면서 내부 조합만 랜덤화한다.
- **대륙 전체의 지질·동굴망:** 커스텀 노이즈와 밀도 함수까지 다루어야 하므로 1차 범위에서는 제외한다.

따라서 프로젝트에는 `자동 자연 동굴 + 수작업 랜드마크 동굴` 혼합안이 현실적이다. 동굴 입구는 지상 진행 경로에 고정하고, 내부는 지하 구조물이 주변 자연 동굴과 교차하지 않도록 보호 경계와 생성 검사를 둔다.

### 7.5 단계별 권고 범위

1. 좌표 사각형으로 2~3개 지역을 만들고 같은 바이옴의 스폰 풀이 달라지는지 검증한다.
2. 자연 동굴용 스폰 조건을 높이·광량·블록별로 나눈다.
3. 고정 입구와 5~10개 직소 조각으로 작은 탐험 동굴 하나를 만든다.
4. 도시와 동굴 사이에 본가식 `route_id`와 스토리 플래그를 연결한다.
5. 플레이 테스트 후에만 커스텀 대륙 생성기나 전용 차원을 검토한다.

## 8 저장 데이터 초안

| 필드 | 설명 |
|------|------|
| `city_id` | 중복되지 않는 도시 식별자 |
| `region_id` | 소속 지방 |
| `route_id` | 소속 도로·필드 구역, 없으면 비어 있음 |
| `habitat_profile` | 지상·동굴·수중 등 서식지 프로필 |
| `anchor_x`, `anchor_z` | 설계상 기준 좌표 |
| `placed_x`, `placed_y`, `placed_z` | 실제 배치 좌표 |
| `biome_profile` | 선택된 도시 외형 프로필 |
| `structure_version` | 배치에 사용한 구조물 버전 |
| `generation_state` | 미생성, 생성 중, 생성 완료, 손상, 복구 필요 |
| `bounds` | 충돌 검사와 복구에 사용할 도시 경계 |
| `npc_markers` | 영구 NPC 기준 위치와 역할 |

## 9 검증 항목

- 같은 시드와 설정에서 도시 좌표와 외형이 동일한가?
- 필수 도시가 바다·절벽·구조물 충돌로 누락되지 않는가?
- 체육관, 센터와 상점이 항상 같은 도시 경계 안에 있는가?
- 새 청크 생성과 서버 재시작이 도시를 중복 생성하지 않는가?
- 기존 월드의 플레이어 건축물을 감지하고 생성을 중단할 수 있는가?
- 구조물 업데이트가 기존 도시를 자동으로 덮어쓰지 않는가?
- 손상된 핵심 블록과 NPC를 관리자 명령으로 복구할 수 있는가?
- 같은 바이옴이더라도 지역과 서식지에 따라 의도한 스폰 풀이 적용되는가?
- 자연 동굴과 랜드마크 동굴을 스폰 조건이 올바르게 구분하는가?
- 필수 이동 회랑과 동굴 출구가 지형 생성으로 막히지 않는가?

## 10 미결정 사항

- D-04: 고정 좌표 목록, 격자, 동심원 또는 혼합 배치 중 무엇을 사용할 것인가?
- D-05: 새 월드만 지원할지 기존 월드의 미생성 청크까지 지원할 것인가?
- 후보 탐색 반경과 최대 시도 횟수는 얼마인가?
- 허용·제외 바이옴과 최대 경사 기준은 무엇인가?
- 도시 전체를 한 번에 배치할지 청크 생성 과정에서 나눠 배치할 것인가?
- 구조물 손상 판정과 복구의 최소 단위는 무엇인가?
- 지역 경계를 좌표 사각형, 격자, 다각형 또는 커스텀 바이옴 중 무엇으로 표현할 것인가?
- 플레이어별 진행 상태를 야생 스폰에 반영할지 월드 공통 상태만 사용할 것인가?
- 첫 버전에 고정 월드나 전용 차원을 포함할 것인가?
