# 포켓몬 스폰 프로필

> 관련 요구사항: F-06, F-07
>
> 관련 결정: 세대 월드의 스폰은 세대 중심 혼합 방식 사용
>
> 설계 상태: 기술 조사 진행 / 대상 Cobblemon 버전 고정 필요

## 1 목적

Cobblemon이 제공하는 바이옴, 시간, 날씨, 높이와 블록 기반 서식지 규칙은 최대한 유지하면서 각 스폰 엔트리에 출현 가능한 세대 차원을 명시한다. 기본 스폰과 프로젝트 스폰이 중복되어 다른 세대 월드에 포켓몬이 섞이는 것을 방지한다.

## 2 확인된 원본 구조

Cobblemon의 자연 스폰은 `data/cobblemon/spawn_pool_world` 아래의 포켓몬별 JSON으로 정의된다. 한 파일에는 같은 포켓몬의 지상, 수중, 동굴, 구조물 등 여러 스폰 엔트리가 들어갈 수 있다.

종 데이터는 `data/cobblemon/species/generation1`, `generation2`처럼 세대별 디렉터리로 구분되어 있어 기본 도입 세대를 기계적으로 추출할 수 있다.

그러나 세대 할당을 파일 단위로만 처리하면 안 된다. 지역 폼, 특수 폼과 조건부 개체는 원종의 스폰 파일 안에 함께 들어갈 수 있으므로 실제 `spawns[]` 엔트리의 `pokemon` 선택자를 기준으로 예외를 적용한다.

## 3 단순 추가 방식의 문제

프로젝트 네임스페이스에 세대별 스폰 JSON을 추가하기만 하면 Cobblemon 기본 스폰 파일도 계속 로드된다. 기본 파일에 차원 제한이 없으면 같은 바이옴을 사용하는 모든 세대 월드에서 기본 엔트리가 후보가 된다.

따라서 다음 중 하나가 필요하다.

1. 데이터팩 필터로 Cobblemon 기본 `spawn_pool_world`를 차단하고 생성된 전체 스폰 풀로 대체한다.
2. 코어 모드가 리소스 로딩 또는 스폰 판정 시 기존 엔트리에 세대 차원 조건을 주입한다.

첫 구현은 결과물을 사람이 확인하고 테스트할 수 있는 **생성형 데이터팩 방식**을 우선 검토한다. 런타임 주입은 원본 데이터 재배포와 업데이트 비용을 줄일 수 있지만 Cobblemon 내부 API 변경에 더 민감하다.

## 4 데이터 변환 모델

```text
고정된 Cobblemon 버전의 원본 스폰 엔트리
  + 종 데이터에서 추출한 기본 세대
  + 지역 폼·특수 개체 예외표
  + 프로젝트 월드 프로필과 밸런스 조정
  = 차원 조건이 포함된 프로젝트 스폰 엔트리
```

원본의 다음 조건은 기본적으로 보존한다.

- 바이옴과 바이옴 태그
- 지상, 수중, 수면 등 스폰 위치 유형
- 시간, 날씨와 달 위상
- 고도, 광량과 하늘 노출
- 주변·바닥 블록과 구조물
- 희귀도 버킷, 가중치와 레벨 범위

변환기는 각 엔트리의 `condition.dimensions`에 허용된 세대 차원 ID를 추가한다. 월드별 레벨이나 가중치가 다르면 엔트리를 복제하고 ID에 월드 접미사를 붙인다.

```json
{
  "id": "squirtle-1-generation1",
  "pokemon": "squirtle",
  "condition": {
    "dimensions": [
      "cobbleventure:generation_1"
    ],
    "biomes": [
      "#cobblemon:is_freshwater"
    ]
  }
}
```

## 5 프로젝트 입력 데이터

생성된 JSON을 직접 수정하지 않고 다음과 같은 원본 테이블을 관리한다.

| 필드 | 설명 |
|------|------|
| `pokemon_selector` | 종, 폼과 속성을 포함한 Cobblemon 선택자 |
| `native_generation` | 종 또는 폼이 처음 등장한 세대 |
| `world_profiles` | 실제 출현을 허용할 세대 월드 목록 |
| `habitat_policy` | 원본 서식지 보존, 추가 또는 교체 |
| `weight_scale` | 월드별 원본 가중치 배율 |
| `level_override` | 월드별 레벨 범위 재정의 |
| `include_transition` | 챔피언로드 출현 허용 여부 |
| `notes` | 지역 폼, 진화 계통과 예외 사유 |

세대별 월드 구성 방식은 다음 세 안을 비교했다.

| 정책 | 설명 |
|------|------|
| 세대 전용 | 해당 세대에 처음 등장한 포켓몬만 출현 |
| 누적 | 현재 세대와 이전 세대 포켓몬이 모두 출현 |
| 세대 중심 혼합 | 해당 세대가 중심이지만 생태와 게임 밸런스에 맞는 다른 세대도 일부 출현 |

현재 요구사항인 “월드마다 조금씩 다름”에 맞춰 **세대 중심 혼합**을 채택한다. 해당 세대 포켓몬을 중심으로 구성하되 생태, 진화 계통과 게임 밸런스에 맞는 다른 세대 포켓몬도 일부 배치한다. 정확한 비율은 플레이 테스트 후 정한다.

던전 차원은 소속 세대 월드의 프로필을 기본으로 상속한 뒤 던전 고유 포켓몬과 희귀도 배율을 덮어쓴다. 예를 들어 1세대 달맞이산 구역은 1세대 혼합 프로필을 기반으로 동굴·운석·요정 테마 포켓몬의 가중치를 높인다.

## 6 원본 차원 조건 처리

원본 엔트리에 이미 `dimensions`가 있는 경우 무조건 덮어쓰거나 단순히 합치지 않는다. 네더·엔드 전용 서식지가 세대 오버월드로 이동하거나, 반대로 바닐라 차원에 계속 출현하는 문제가 생길 수 있다.

다음 변환표를 별도로 정의한다.

```text
원본 오버월드 서식지 → 허용된 generation_N 차원
원본 네더 서식지     → 유지, 세대 월드로 이전 또는 별도 차원 중 결정
원본 엔드 서식지     → 유지, 세대 월드로 이전 또는 별도 차원 중 결정
챔피언로드 서식지    → transition의 해당 league_bounds
```

## 7 생성 및 검증 절차

1. 프로젝트가 지원하는 Cobblemon 버전과 원본 파일 해시를 고정한다.
2. 해당 버전의 종 디렉터리에서 기본 세대 매핑을 추출한다.
3. 모든 `spawn_pool_world` 엔트리를 읽고 지역 폼 예외표를 적용한다.
4. 월드 프로필에 따라 차원 조건, ID 접미사와 밸런스 값을 생성한다.
5. 데이터팩 필터와 생성된 스폰 파일을 출력한다.
6. 정적 검증과 실제 게임 명령으로 결과를 확인한다.

필수 정적 검증 항목은 다음과 같다.

- 모든 활성 스폰 엔트리에 허용 차원 또는 명시적 예외가 있는가?
- 존재하지 않는 차원 ID나 바이옴 태그를 참조하지 않는가?
- 스폰 ID가 중복되지 않는가?
- 지원 대상 포켓몬과 폼이 최소 하나의 월드 프로필에 배정됐는가?
- 필터링 후 원본 기본 스폰이 다시 섞이지 않는가?
- Cobblemon 버전 갱신 후 추가·삭제·변경된 원본 엔트리를 보고하는가?

게임 내에서는 각 세대 월드와 챔피언로드에서 `/checkspawn` 계열 명령으로 후보 목록과 비율을 검증한다.

## 8 업데이트와 라이선스

Cobblemon 업데이트 때 원본 스폰 파일이 변경될 수 있으므로 생성기는 버전과 해시가 다르면 자동 생성을 중단하고 차이 보고서를 출력해야 한다. 생성 결과에 원본 데이터를 포함하거나 수정본을 배포할 때는 Cobblemon의 해당 버전 라이선스와 데이터·에셋 재배포 조건을 별도로 확인한다.

가능하면 원본 전체를 프로젝트에 수동 복사하지 않고, 빌드 시 고정된 Cobblemon 의존 파일에서 필요한 데이터를 읽어 변환하는 방식을 검토한다.

## 9 미결정 사항

- 세대 중심 혼합에서 해당 세대와 다른 세대의 목표 비중을 얼마로 할 것인가?
- 지역 폼을 원종 세대와 폼 도입 세대 중 어디에 배치할 것인가?
- 네더와 엔드 전용 포켓몬을 세대 월드에서 어떻게 제공할 것인가?
- 진화 전후 포켓몬을 같은 세대 월드와 서식지에 항상 묶을 것인가?
- 기본 스폰 파일 필터와 런타임 주입 중 어떤 방식을 채택할 것인가?
- 원본 데이터 변환과 수정본 배포가 라이선스 조건에 맞는가?
