# 모듈식 아키텍처와 의존성 경계

> 관련 결정: D-32, D-33
>
> 설계 상태: 기준 결정 / 플랫폼 독립 코어 착수

## 1 목적

Cobbleventure를 특정 모드팩의 확장이 아니라 독립 어드벤처 시스템으로 개발한다. Cobblemon 안정 버전이 확정되기 전에도 지역, 진행, 차원 연결, 트레이너 계약과 전투 AI를 구현하고 검증할 수 있어야 한다.

## 2 의존성 방향

```text
콘텐츠 JSON·구조물·리소스
             ↓
플랫폼 독립 코어
├─ adventure-api
├─ region-engine
├─ progression-engine
├─ travel-engine
└─ battle-ai
             ↑
게임 어댑터
├─ minecraft-fabric
├─ cobblemon
└─ trainer-<provider>
             ↑
선택 호환성 프로필
└─ cobbleverse
```

화살표 아래쪽 구성요소는 위쪽 구성요소를 의존할 수 있지만 반대 방향은 금지한다. 플랫폼 독립 코어의 컴파일·테스트 클래스패스에는 Minecraft, Fabric, Cobblemon과 트레이너 모드를 넣지 않는다.

## 3 물리 모듈 분리 기준

다음 중 하나를 만족할 때 별도 코드 모듈로 분리한다.

- 독립적으로 설치·제거하거나 교체해야 한다.
- 외부 모드 의존성이 다르다.
- 저장·초기화·장애 복구 수명주기가 다르다.
- 다른 모듈이 재사용할 안정적인 계약을 제공한다.

지방, 지역, 던전과 리그마다 별도 JAR을 만들지는 않는다. 같은 엔진으로 해석할 수 있는 차이는 콘텐츠 팩으로 표현한다.

## 4 코드와 데이터의 책임

| 코드가 담당하는 것 | 데이터가 담당하는 것 |
|--------------------|-----------------------|
| JSON 구문·의미·교차 참조 검증 | 지역 경계와 바이옴 풀 |
| 지역 겹침과 연결 그래프 검사 | 벽·관문·도시·체육관 앵커 |
| 진행 상태 전이와 권한 판정 | 배지·퀘스트 등 진행 조건 ID |
| 귀환·복구 불변 조건 | 차원·입구·목적지 연결 |
| 게임 API 호출과 오류 변환 | 트레이너·보상·스폰 프로필 참조 |

JSON은 벽을 직접 생성하지 않는다. `boundary.type`, 템플릿과 보호 프로필을 선언하고 게임 어댑터가 실제 블록 배치와 이동 제한을 수행한다.

## 5 현재 구현 순서

1. 지역 JSON 모델, 로더와 단일·집합 검증
2. 지역 연결 그래프와 진행 조건 표현식
3. 차원 입구, 목적지, 귀환점과 체크포인트 계약
4. 트레이너·보상·스폰 프로필의 공통 ID 참조 검사
5. 콘텐츠 팩 버전과 마이그레이션 검사
6. Cobblemon 안정 버전 확정 후 최소 게임 어댑터

첫 구현은 [Cobbleventure Core](../../projects/cobbleventure-core/README.md)에 있다. 지역 파일의 기계 판독 계약은 [지역 JSON Schema](../../content/schemas/region.schema.json), 예제는 [첫 지역 정의](../../content/regions/generation_1/region_01.json)를 기준으로 한다.

## 6 호환성 원칙

- Cobbleverse는 필수 의존성이 아니라 선택 호환성 프로필이다.
- 트레이너 기능은 내부 공통 계약을 두고 공급자별 어댑터로 연결한다.
- 어댑터가 없는 환경에서도 코어 데이터 검사와 시뮬레이션은 실행되어야 한다.
- 외부 API 버전이 바뀌어도 콘텐츠 스키마를 불필요하게 변경하지 않는다.
- 어댑터가 지원하지 않는 기능은 조용히 무시하지 않고 기능 ID와 원인을 보고한다.
